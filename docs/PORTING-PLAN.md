# Portlight Rust port

Source of truth: the Python game at `mcp-tool-shop-org/portlight`, commit `9b02494cca9cd8f58c4531c41f75be02c9720e43` on `main` (about 46k lines under `src/portlight/`, 183 Python files including tests). This repository is the Rust port. Stage 1 is the rules and simulation. Stage 2 is a dimetric (2:1) chart on top of that simulation. The first playable is in: Mediterranean, four ports, sail Porto Novo to Al-Manar, dock, and trade. It has no harbour scene, terrain, weather, or NPC ships.

The simulation crate (`portlight-sim`) has no terminal, TUI, or graphics dependency. `portlight-cli` and the Godot view both drive it through `Session`.

## Deterministic core

A run is determined by:

1. **Content.** The JSON snapshot of the Python catalogs at commit `9b02494`.
2. **Seed.** `new_game` stores `world.seed` as an `i128`. `PyRandom::from_seed` follows CPython: absolute value, split into little-endian 32-bit words. That covers every `u64`, `2**63`, and `i128::MIN` (magnitude `2**127`). Python also accepts integers outside `i128`; the script and CLI reject those with `Invalid number`. The runner builds `Random(seed)` once and threads it through market ticks and voyage days, matching `GameSession.new`.
3. **RNG algorithm.** `pyrand.rs` is CPython's MT19937 (`_random`): `init_by_array` seeding, `random()` (53-bit), `getrandbits`, `_randbelow`, `randint`, `choice`, and weighted `choices` with `bisect_right` and `hi = n - 1`. It was checked against CPython 3.12.3, including `Random(2**70 + 12345)`.
4. **Rounding.** Prices and several voyage formulas use Python 3 `round` (half away from zero, then half-to-even when the value is exactly halfway) and `int()` truncation. Rust's `f64::round` alone is not enough; `util::py_round` follows CPython's `float.__round__`.

Exact parity is possible for any code path that only uses those RNG calls and the ported rules. It is not blocked by the RNG. The goldens lock the ported `Session::advance`, including the systems merged after the first slice. Hunting and bounties are merged in the sim and offered by the Godot Hunt overlay (#35). `engine/custom_captain.py` and the invariant tests from `stress/` are not started. `engine/underworld.py` and `engine/merchant.py` are deprioritized, because the Python session never calls them. The TUI is not ported. The Godot view replaces it, and the screens still open are listed below. |

`Session.advance` calls `tick_markets` without `current_day`, so seasonal stock drains never run on that path (`current_day` defaults to 0). Voyage danger and speed do use the season. The Rust market tick accepts a day and applies seasons when it is non-zero; the script runner passes 0 so it matches the session.

## What the script runner includes

`portlight script` and `tools/parity/oracle.py` share one action language:

```
new <captain_type> <name> <seed> [port]
buy <good> <qty>
sell <good> <qty>
depart <port_id>
advance
```

For each command the oracle calls the Python engine and the Rust runner calls the port. Both then apply the same session-level steps:

- **new.** `new_game`. RNG is `Random(seed)`. The contract board is drawn from `Random(seed + 7919)`, then the session RNG is restored. The Godot Contracts screen (#33) shows the board.
- **buy / sell.** `execute_buy` / `execute_sell`, then reprice that port with the captain's modifiers. Sell also runs `record_trade_outcome`, including the session's post-sale cost-basis estimate.
- **depart.** `depart`, including the captain port-fee multiplier and ship-class block.
- **advance, in port.** Heat decay, `tick_markets` for one day, day and provision and wage updates, reprice every port with captain modifiers.
- **advance, at sea.** Heat decay, `advance_day`, inspection reputation, `arrive` plus arrival reputation when the ship reaches the destination, reprice every port. A pending pirate duel returns no events and does not spend the day. `advance` does not auto-resolve, matching `auto_resolve_duels = False`.
- **hire / provision.** `GameSession.hire_crew` and `GameSession.provision`, including the service-cost modifier on provisions and named specialist officers.
- **work.** `GameSession.work` / `work_docks`: one `randint(3, 5)` on the session RNG, silver added, then `world.day` set from `captain.day`. Markets, provisions, wages, and reputation do not tick. That is the dock-work safety valve.
- **duel / resolve_duel.** `portlight duel` (`engine/duel.py` `resolve_duel`) and `GameSession._resolve_pending_duel` (five random stances, then the same resolver). Both apply `silver_delta`, leave `standing_delta` off the reputation record, and clear `pending_duel`.

The comparison also covers contract offers, infrastructure purchases (deposit, withdraw, repay, license purchase, insurance claims, credit default, and warehouse seizure, as well as the earlier warehouse, broker, and hull-policy purchases), credit draws, injuries, sea-culture enrichment (it draws from the same RNG after `advance_day`), arrival prose, consequences, milestone evaluation, narrative beats, the interactive encounter machine (`negotiate` / `flee` / `fight`, naval rounds, boarding, `engine/combat.py`), prize `capture` (the `capture_*.txt` scripts, including a crew count that is too small, one that is too large, letting the prize go, a fleet that is not full, and a fleet that is full), area 7a (`rename_ship`, `dock_current_ship`, `board_fleet_ship`, `sell_fleet_ship`, `fire`, `abandon_contract`, single-ship `repair`), and area 7b (`hunt`, `bounty` list / accept / hunt / claim, and the wanted-level-3 bounty-hunter sea event). Those systems are merged in the sim. Which of them the Godot view offers is listed under "Porting order". `Session::sell` writes a fulfilled contract onto the books. Callers do not use `books_mut()` for that.

Save and load are not locked by the golden files. The oracle job understands `save <slot>` and `load <slot>`, and for every script that starts a game it also round-trips the final state: Rust's slot loaded by Python, Python's slot loaded by Rust, and a same-side reload on each side. Those loaded snapshots are compared with each other. The round-trip stops at load: it does not `advance` the loaded game, and the Python save is `oracle.py` `do_save`, not `GameSession.save`. Load recalculates port prices with the captain's modifiers, so a loaded game is not required to match the pre-save snapshot. The live snapshot adds the contract board (offers, active, breaches), captain memories, active bounties, deferred fees, and the ledger. `PORTLIGHT_WIDE_SNAPSHOT=1` is what emits those keys from Rust. The golden comparison strips them, so `parity/golden/` stays the narrow shape. `parity/expected_divergences.json` names any live check that is a known Rust-versus-Python divergence, and the leaf JSON paths that may differ, each with the Python and Rust values. A round-trip entry is checked the same way. A path that names a list or object is rejected, and a `[*]` wildcard is rejected with that reason rather than a traceback. CI prints that list. Any other difference in that script fails the check. Contract-board `board_effects` is passed from session refresh and the oracle, so `broker_board.txt` matches `GameSession`. The remaining listed row is the capture log on `capture_prize.txt`.

## Public session

`portlight_sim::Session` is the API a gdext front end drives. It is stable for that consumer:

| Method | Role |
| --- | --- |
| `Session::new(name, captain_type, seed, starting_port)` | New game. `seed` is an `i128`. |
| `world()` | Ports (`map_x`, `map_y`), ship, cargo, voyage, standing. |
| `sail_lanes()` | Picker lanes, including blocked ones and raw-speed day estimates. |
| `victory()` | The four victory paths. A played game can complete a path when the sim records contracts. The Godot view does not offer that play. |
| `books()` / `books_mut()` | Ledger plus contract, license, warehouse, broker, policy, and credit records. Buy and sell update the ledger. The Godot Contracts (#33) and Harbour (#38) desks call the `Session` methods that grant the contract, license, warehouse, broker, policy, and credit records. `books_mut()` stays a test seam. |
| `buy` / `sell` / `depart` / `advance` | One action. `advance` returns `Turn { events, shocks }`. A pending duel makes `advance` return no events and leave the day unchanged. |
| `hire_crew(count, role)` / `provision(days)` | Port hiring and provisions. Sailors use `crew_cost`. Specialists cost `wage * 10` and get a name and trait. Provisions use `max(1, int(provision_cost * service_modifier))`. |
| `work()` | One day on the docks. Returns 3 to 5 silver. Does not tick markets, provisions, wages, or reputation. |
| `duel(stances)` / `resolve_pending_duel()` | Clear a pending pirate duel. `duel` is the CLI stance fight (`thrust` / `slash` / `parry`, at least three). `resolve_pending_duel` is the bot auto-resolve. Both return `DuelOutcome`. The chart offers this fight. |
| `hunt()` | Hunt or forage. Merged in the sim; the Godot Hunt overlay (#35) calls it. |
| `bounty_board()` / `accept_bounty(id)` / `hunt_bounty(id)` / `claim_bounty(id)` | Bounty board, accept, hunt, and claim. Merged in the sim; the Godot Hunt overlay (#35) calls them. |
| errors | `SimError`. `Display` text is the Python sentence. |

`Session::save` and `Session::load` are merged in the sim. They speak the Python version-12 JSON slot. The Godot new-game screen (#30) and the chart Save button call them. Do not add a second format in the UI crate.

`run_script` only calls these methods, then writes the parity snapshot. The snapshot omits map coordinates on purpose. A map should read `world()`, not the snapshot.

## Known Python quirks

These are real disagreements inside the Python game. The Rust port keeps them. A later UI should call `sail_lanes` rather than "correcting" the numbers.

**Sail-picker days ignore modifiers.** `execute_sail_flow`, `routes_view`, `formatting.travel_time`, and `_estimate_sail_days` all estimate days as `max(1, round(distance / speed))` where `speed` is the template `ship.speed`. They do not apply crew ratio, morale, season, captain speed bonus, or the event modifier that `advance_day` uses. From Porto Novo a coastal sloop (speed 8) shows Ironhaven (distance 36) as 4 days, because `round(4.5)` is 4. The sea day applies those modifiers, so the sailed progress is a different number. `sail_lanes` returns 4.

When there is no ship the three call sites disagree on the fallback speed: the TUI picker uses 5, `routes_view` uses 4, and `_estimate_sail_days` uses 6. `sail_lanes` uses 5. `new_game` always fits a ship, so that fallback is unused on the ported path.

**The picker lists lanes that `depart` then blocks.** Both the TUI picker and `routes_view` show every direct route from the current port, including a rank gap of 2 or more. Suitability only changes the min-ship color. `depart` returns the `BLOCKED` string and stays in port. A gap of 1 is a warning: the lane is listed, sailing is allowed, and danger is multiplied by 1.5. A sloop at Sun Harbor still sees the galleon lane to Crosswind Isle, and `depart("crosswind_isle")` refuses it.

`routes_view` keeps catalog order. The TUI picker stable-sorts by distance. `sail_lanes` follows the TUI sort. Provisions shown in the routes table are estimated days plus 2; that buffer is on `SailLane.provisions_needed`.

**Victory path id `commercial_empire` versus milestone family `commercial_finance`.** These are not two names for a rename that should be collapsed. `VictoryPathStatus.path_id`, `COMPLETION_SUMMARIES`, `CANDIDATE_BOOSTS`, and the TUI `_PATH_NAMES` key are `commercial_empire`. `MilestoneFamily.COMMERCIAL_FINANCE` and `PROFILE_MILESTONE_FAMILIES` use `commercial_finance`. The other three victory path ids (`lawful_house`, `shadow_network`, `oceanic_reach`) match a milestone family of the same string. The Rust evaluators keep both strings. `commercial_finance` is not a path id.

**Contract outcome trust, standing, and heat are computed but never applied.** `engine/contracts.py` puts `trust_delta`, `standing_delta`, and `heat_delta` on every `ContractOutcome` (completed, completed_bonus, expired, abandoned), but `GameSession` adds only `silver_delta` to the captain (`app/session.py:651-653` on a sale, `:715-717` on expiry, nothing on abandon at `:1628-1637`). The three deltas are read in one gameplay place: sizing a `contract_failure` insurance claim (`app/session.py:721`, `abs(trust) * 50 + abs(standing) * 30`). The Rust port keeps this: `note_contract_on_books` applies silver only, and `file_contract_claims` is the only reader. The parity goldens lock it (`contract_expire.json` ends with trust, standing, and heat unchanged). Godot outcome copy prints the Silver term only, so it never shows a change that does not happen.

## Deliberate divergence (Mike-authorized)

**Hunt fight crew loss.** Python costs crew at the enemy rake (naval.py:318-351)
and at boarding (encounter.py:246-266). A starter boarding a bounty target always
lands in the (3,6) bracket and keeps 1 crew. In a hunt fight (enemy is an
active, unclaimed bounty: active_bounties has enemy_captain_id, claimed_bounties
does not) Rust drops the enemy rake's crew result (roll still drawn, hull damage
kept) and re-reads the boarding player roll r in lo..hi as
0 if r == 0, else min(cap, floor(0.15 + 0.025*crew + (r - lo + 0.5)/n), r),
cap = max(1, ceil(0.03*crew)) floored at template_crew_min
(naval::hunt_crew_loss_cap). Same draws, same order, no save change.
Random sea encounters, scripted encounters and claimed-target fights keep
Python. Pinned in parity/expected_divergences.json: bounty_claim.txt and
bounty_claim_sail.txt.

## Parity harness

**CLI-vs-oracle naval RNG stream.** The real Python CLI seeds naval rounds from a per-turn `random.Random(seed + day×1000 + naval_turns + 7777)` (cli.py:2105-2108). The TUI uses `seed + day×1000 + naval_turns + duel_turns`. The parity oracle and Rust use the session stream. Rust matches the oracle, not the CLI's naval RNG.


Regenerate content and goldens from a Python checkout of commit `9b02494`:

```
PYTHONPATH=/path/to/portlight/src python3 tools/extract_content.py
cargo build --locked -p portlight-cli
PYTHONPATH=/path/to/portlight/src python3 tools/parity/check.py --write-golden
PYTHONPATH=/path/to/portlight/src python3 tools/parity/victory_cases.py
```

`python3 tools/parity/check.py` diffs the live oracle against the Rust binary when `portlight` imports, and always diffs Rust against `parity/golden/`. The live diff uses the wide snapshot (board, memories, bounties, deferred fees, ledger). The golden diff uses the narrow snapshot, so `--write-golden` does not add those keys. `--write-golden` reproduces an unchanged golden byte for byte, including `_source` and `_note`. The same command also runs `tools/parity/session_runner.py` (a real `GameSession`) on scripts whose verbs the session implements, and the save/load round-trip described above. `--require-oracle` exits non-zero when that import fails, instead of falling back to goldens. `cargo test` does the golden comparison with no Python installed. Those tests, including `save_parity::snap`, clear `PORTLIGHT_WIDE_SNAPSHOT` before serializing, so a shell that exported it does not widen the golden diff. CI does not set the variable. Goldens were produced with CPython 3.12.3. CI checks out commit `9b02494`, runs `check.py --require-oracle`, and re-runs `victory_cases.py --check` against the committed JSON. The Rust toolchain is pinned in `rust-toolchain.toml` (1.98.1) and CI passes `--locked`.

### Display

Chart coordinates stay on the 50×36 grid. The view rotates them and never writes them back. The rotation is the one in the asset spec, which replaces the unrotated `sx = (x − y) · 64` formula:

```
u = (x + y) / √2
v = (y − x) / √2
screen_x = (u − v) · 64
screen_y = (u + v) · 32
```

Cells are 128×64. Chart water sits on integer `(u, v)`. Ports and the ship sit at the fractional `(u, v)` of their chart point. Porto Novo `(18, 8)` is about `(1629.2, 362.0)`. A ship has one sort point, not a grid footprint. Facing is `round(atan2(dv, du) / 45°)` in `(u, v)`, eight buckets, `k = 0` along +u (screen down-right). A bucket edge holds the previous facing for 5°. Before the first voyage the bow is `f1` (screen down). The Grain Road, Porto Novo to Al-Manar, is `(du, dv) ≈ (2.828, −5.657)`, so `k = 7` (about 9.5° above screen-right). Docked, the ship is drawn at the port anchor plus `(32, 16)`.

`godot/project.godot` sets `rendering/viewport/hdr_2d=false` on purpose. That is the Godot default, and it stays written down so a later save cannot drift into HDR 2D. Approved tiles were gated under sRGB 2D blending. HDR 2D draws the canvas in linear space and would invalidate that gate.

Chart sprites follow asset-spec Rev 4, R11, copied from each plate's `import` object in `MANIFEST.json`. Import is lossless (`compress/mode=0`), Fix Alpha Border on (`process/fix_alpha_border=true`), premultiplied alpha off, and VRAM compressed textures off (`vram_texture` false). Mipmaps are on for `chart_water_a`, `chart_water_b`, and `chart_water_c` only, and off for `chart_port_marker` and every ship and harbour plate. The project canvas filter is Nearest (`rendering/textures/canvas_textures/default_texture_filter=0`), so a sprite drawn at 1:1 shows the plate pixels. Those settings live in each `godot/assets/landing/**/*.png.import`.

`godot/assets/landing/` is the whole approved v0.3.0 bundle: 36 ship plates (sloop, cutter, brigantine, and galleon, each with `f0`–`f7` and a wake), 30 harbour plates, and 4 chart plates (`chart_water_a`–`c` at 128×64 and `chart_port_marker` at 128×128), plus `MANIFEST.json`. The chart draws the player's ship class, the chart-water tiles, and the port marker. Template ids map to plates: `coastal_sloop` → `ship_sloop`, `swift_cutter` → `ship_cutter`, `trade_brigantine` → `ship_brigantine`, `merchant_galleon` → `ship_galleon`, each with `f0`–`f7` and a wake. Canvas and anchor come from that plate's MANIFEST entry (the sloop is `(32, 50)` on a `64×64` canvas, hull length 40). `royal_man_of_war` has no plate: it is drawn with the galleon plates and the panel says `Man-of-war`. An unknown class, or no ship, uses the sloop plates and logs a warning once (`<none>` when the id is empty). The port marker anchor is `(64, 95)` from its render sidecar. Facing still comes from the rotated `(u, v)` heading. The class wake is drawn under the hull while the ship is at sea, and omitted when docked. Docked placement is still the port anchor plus `(32, 16)` for every class. `portlight-chart` checks that `MANIFEST.json` (sha256 `f8d735fb035039c808a113e5bd5d771a3070f87b863f13ea4c77c903f930ca31`) and every entry's sha256 match the committed files, and that the on-disk PNG set is exactly those 70 paths. Harbour entries use `group` `"harbour"` and keep the old group name in `subgroup`. The same test checks each landing `.import` against that entry's `import` fields, plus `viewport/hdr_2d=false` and `textures/canvas_textures/default_texture_filter=0` in `project.godot`. The manifest is generated and is not hand-edited. The placeholder generator skips any plate whose note is not `PLACEHOLDER`, so it cannot rewrite the landing PNGs.

Chart water and the port marker are the approved landing plates (`chart_water_a`–`c`, `chart_port_marker`). Chart and harbour water pick a variant with `water_variant`, a stable hash of the cell, not `(col + row) % 3`. Ship ids are `ship_<class>_f0`..`f7` and `ship_<class>_wake` for sloop, cutter, brigantine, and galleon. Harbour water, quay, pier, and pilings from the same bundle are committed for later. They use the art-director datum of −48 px (layer offset `+48` because Godot Y grows down). Chart water is a separate 128×64 plate and is not shifted. There is no harbour scene in the first playable. `godot/scenes/harbour_seam.tscn` is a separate seam plate and is not the main scene. The scene file places nothing itself. `HarbourSeam` draws harbour water, `quay_1111`, a one-corner pier whose root cell is water, and pilings on a separate open water cell. Placement is `grid_to_screen` (`sx = (col − row) * 128`, `sy = (col + row) * 64` for a 256×128 cell) plus the −48 datum. Water is its own layer and runs past the viewport, and past the chart camera, so the 8 px tip feather stays off screen.
